# Grademaxxing for iOS

Native SwiftUI work for Grademaxxing lives here. This is a first implementation with a native gradebook, not a web wrapper. It uses the existing Grademaxxing backend without changing the web application or its StudentVUE adapter.

See [the implementation plan](PLAN.md) for the full roadmap and [validation evidence](VALIDATION.md) for what has actually been checked.

## First implementation

- Native sign-in, saved-session restoration, foreground keepalive, password-only reconnect, and sign-out.
- Grades home, reporting-period picker, official course marks, category totals, searchable assignments, and assignment details.
- A local what-if calculator that adds a hypothetical assignment to authoritative category totals. It refuses to project when required values are missing or the calculated baseline differs from the official mark by more than 0.25 percentage points.
- An assignment planner for editing scores, exclusion, extra credit, and hypothetical work, with reset and target-score estimates. Native assignment-date charts are anchored to the current official mark and labeled as estimated history.
- Editable current-course GPA planner following the web app's explicitly provisional PUSD scale, with credits, inclusion, and rigor choices.
- A native School tab with attendance history and period details, official course totals, an event calendar with month navigation, schedule, and student profile.
- Searchable documents and a read-only mailbox with folder/unread filters, native message text, explicit HTTPS links, on-demand attachments, and native file previews.
- Synthetic demo mode, native loading/empty/error states, accessibility identifiers, and Dynamic Type text.

Profile photos, persistent record caching, push notifications, and a distribution build remain on the roadmap. Mail bodies render as native text; messages containing images offer an explicit StudentVUE link for their complete content. Inline file previews support PDF, PNG, JPEG, GIF, and WebP; unsupported formats offer the official portal link.

## Open in Xcode

Open `Grademaxxing.xcodeproj`. The shared `Grademaxxing` scheme targets iPhone with iOS 17 or later and Swift 6. Its default Run argument is `--demo`, so the first run uses invented records and makes no school requests. To use the connected flow later, disable that argument under **Product → Scheme → Edit Scheme → Run → Arguments**.

Choose an installed iPhone simulator and run. For a physical phone, select your Apple Developer team in the target's **Signing & Capabilities** settings, and choose an available bundle identifier. No signing team or credentials are checked in.

An iOS build requires full Xcode and an installed simulator runtime; Command Line Tools alone are insufficient. After installing Xcode, the simulator build command is:

```sh
xcodebuild -project Grademaxxing.xcodeproj -scheme Grademaxxing \
  -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath DerivedData CODE_SIGNING_ALLOWED=NO build
```

`App/Info.plist` configures `GrademaxxingAPIOrigin`, initially `https://dev.grademaxxing.app` for pre-production. Set this deliberately to the approved HTTPS origin when validating a deployment. The client rejects HTTP, embedded credentials, and non-origin API addresses. It never follows redirects while carrying a session. District portal credentials must only go to the intended Grademaxxing deployment.

The shared scheme also includes the `GrademaxxingUITests` target. Once a simulator is available, use **Product → Test** to run the seven synthetic cases for what-if versus official grades, assignment editing/reset, reporting-period switching and assignment search, school records/month navigation, document/mail/attachment preview navigation, planner inclusion/reset, and leaving the demo. Their source is syntax-checked here but has not been compiled or run with XCTest. They explicitly launch with `--demo`; they must never be repurposed to screenshot a live student account.

## Checks without Xcode

Run from this directory:

```sh
swift run GrademaxxingChecks
swift build --product GrademaxxingPreview
python3 scripts/generate-project.py --check
bash scripts/check-catalyst.sh
```

`GrademaxxingChecks` is an executable Swift test suite so it works even with Command Line Tools, which lacks XCTest and Swift Testing. It exercises API requests, session rotation/restoration/expiry/logout, concurrency, XML contracts, and calculation behavior. All transport responses and credentials are synthetic. No live school requests, Keychain secrets, or external dependencies are involved.

The current suite contains 73 checks, including ten assignment-planning cases generated by the actual web rules, backend attendance/document contract fidelity, mail text and unread semantics, all implemented resource endpoints, real URLSession response bounds with a synthetic URLProtocol, file signature/type/size validation, private temporary-file lifecycle, invalidation after account/month changes, and sign-out races involving a slow read and a late login.

`check-catalyst.sh` uses the Mac Catalyst UIKit/Quick Look frameworks shipped in the installed macOS SDK to compile the shared core module and type-check the iOS source branches. It caught and verified a fix for Swift 6 isolation in the Quick Look delegate. It is additional compiler coverage, not an iPhone build, simulator test, or Quick Look runtime test. The script requires an SDK containing those frameworks.

`GrademaxxingPreview` compiles the same SwiftUI views with the macOS SDK. You can run `swift run GrademaxxingPreview --demo` for a local desktop preview. This is useful for development; it does not verify an iOS build or replace iPhone visual and accessibility tests.

The checked-in synthetic JSON contract fixture is emitted by the actual web backend's `gradebookXml` builder. In this standalone repository, regenerate all fixtures with `python3 scripts/regenerate-fixtures.py --web-root /path/to/grademaxxing` from this directory. The TypeScript generators require that separate, installed web checkout. The individual commands below run in the original web repository with these scripts under its `ios/` directory:

```sh
./node_modules/.bin/vite-node ios/scripts/emit-contract-fixture.ts \
  > ios/Tests/GrademaxxingCoreTests/Fixtures/gradebook.json
./node_modules/.bin/vite-node ios/scripts/emit-contract-fixture.ts --attendance \
  > ios/Tests/GrademaxxingCoreTests/Fixtures/attendance.json
npx prettier --write ios/Tests/GrademaxxingCoreTests/Fixtures/*.json
```

The same generator accepts `--documents`, `--mailbox`, and `--message` for their corresponding fixtures. Document and attendance fixtures use the real backend adapters; mail fixtures follow the raw read-only mailbox/message contract. Every fixture is invented.

The Xcode project and shared scheme are generated using only Python's standard library. After adding/removing app Swift files, run `python3 scripts/generate-project.py`. Regeneration replaces project settings, including manual signing changes, so keep your local signing configuration separate or reapply it in Xcode. The generator's check mode verifies source registration; `plutil` verifies syntax. Only `xcodebuild` can prove that Xcode resolves and builds the iOS target.

## Gradebook and GPA parity

Gradebook snapshots stay in memory, scoped to the signed-in session and reporting period, with at most eight periods retained. Selecting a cached period shows its last records immediately and validates headers. Identical marks and course structure can reuse assignment details for up to 30 minutes. Missing raw percentages, changed marks/metadata, expired full-read age, and explicit refreshes require complete data. Header-only checks never extend the complete-read deadline. Visible/resume liveness checks perform a complete read when due, and sign-out/account change clears all snapshots.

The GPA planner now includes the provisional academic weighted pipeline, grade-level eligibility, inclusion, rigor, and credits. Its golden fixture is generated by the owning web GPA functions and checks letter bands, course-name policy rules, exclusion/pass-fail behavior, and credit weighting. Unpublished percentages do not silently enter the default GPA. Automatic refresh updates untouched defaults and preserves intentional local edits; explicit refreshes and period changes reset the plan. To regenerate the shared fixture from the repository root:

```sh
./node_modules/.bin/vite-node ios/scripts/emit-grade-policy-fixture.ts \
  > ios/Tests/GrademaxxingCoreTests/Fixtures/gpa-policy.json
npx prettier --write ios/Tests/GrademaxxingCoreTests/Fixtures/gpa-policy.json
```

## Assignment simulation and trend parity

The assignment planner preserves published score evidence and fixed adjustments for hidden category totals. Untouched scores use precise published percentages when warranted by the web rules; edited scores use the entered points. Missing grading evidence is omitted with a partial-estimate label, while invalid edits to supported scores make the result unavailable. Changes are anchored to the official percentage, which remains unchanged. Assignment edits live only in the presented sheet and are discarded on dismissal. Estimated history uses supported visible assignments grouped by school date, with its latest point anchored to the official mark. To regenerate the shared synthetic expectations from the repository root:

```sh
./node_modules/.bin/vite-node ios/scripts/emit-assignment-fixture.ts > ios/Tests/GrademaxxingCoreTests/Fixtures/assignment-policy.json
npx prettier --write ios/Tests/GrademaxxingCoreTests/Fixtures/assignment-policy.json
```

## Session and record handling

Passwords exist only during login/reconnect and are cleared from the input when submitted. The backend returns an opaque encrypted app-session cookie and a `sessionId`; the native client saves these with the identity in device-only, when-unlocked Keychain. Keychain entries are isolated by service host. The password is never stored. Cookie rotation is captured after successful authenticated responses. Requests include both `Cookie` and `x-grademaxxing-session` and are serialized across suspension points, protecting StudentVUE's mutable reporting-period focus.

The network session is ephemeral, with no disk response cache or shared cookie store. Grade/record lists and planner edits remain in memory. File previews are the deliberate exception: Quick Look receives a private temporary file, with iOS complete file protection, backup exclusion, restricted permissions, and cleanup when closed, on sign-out/reconnect, and on the next launch. Late downloads cannot recreate a dismissed preview. Cleanup errors remain visible with a retry control. Sign-out deletes the saved app session before waiting on a slow request, even when remote revocation fails. Older reads, cookie rotations, or logins cannot restore the signed-out session. App-session expiry clears identity and records; upstream expiry preserves in-memory records and offers reconnect. Root views and presented sheets cover records when inactive; device verification remains required.

Responses are streamed with a 20 MiB JSON limit or 36 MiB file-envelope limit; decoded files are limited to 25 MiB. Actual file signatures and image dimensions/frame counts are validated before writing a preview. Active HTML/SVG and mismatched MIME types are rejected. Filenames are reduced to a safe basename and the detected format's extension. Storage is restricted to the app's preview directory beneath the system temporary directory, and symlink roots are rejected. Only one temporary preview is retained at a time.

The message reader performs pure text processing: scripts, remote frames, styles, and image loads are excluded from the native rendering path. Safe links require an explicit tap. The backend's `GetMessage` request uses `markAsRead: false`; the native app sends only read-only resource GET requests. Mailbox lists reflect the backend's available messages, which currently caps each folder at 500 records.

School resource state is scoped to the current account and invalidated on sign-out/reconnect. Each resource has its own loading/error state and retains its last successful in-memory value when a refresh fails. Attendance uses the backend's normalized records, with period incidents taking priority over a daily present entry. Unknown statuses stay unknown, and missing days are never inferred to be absences. Calendar dates remain calendar dates rather than UTC timestamps; month navigation honors the API's supported year range and invalidates old month responses.

Live school testing requires explicit authorization and a designated test account supplied outside source control. Never save or share real credentials, cookies, response bodies, portal records, or screenshots. Do not add StudentVUE write operations.

## Before distribution

The app icon catalog and privacy manifest are scaffolds. The manifest sets tracking to false and currently lists no required-reason APIs. Its empty collected-data list is not a finalized privacy disclosure: reconcile the complete app/backend data flow with App Store privacy answers before shipping.
