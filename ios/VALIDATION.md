## Defects found and fixed by this run

1. **The app target built for a simulator slice that the local Swift package could not provide.** The generated project set no `ONLY_ACTIVE_ARCH`, so Debug builds compiled the app for both `arm64` and `x86_64` while the `GrademaxxingCore` package product was built for `arm64` only. The `x86_64` compile failed with `module file … is incompatible with this Swift compiler: built for incompatible target` and `Unable to resolve module dependency: 'GrademaxxingCore'`, failing both GitHub Actions runs (`Native iOS checks`, runs 38192021305 and 38192401393) as well as a local reproduction of the same command. `ios/scripts/generate-project.py` now sets `ONLY_ACTIVE_ARCH = YES` for Debug and `NO` for Release, matching Xcode's template default. Verified: before the change the app compiled `arm64` + `x86_64` and failed; after it the app compiles `arm64` only, with no `x86_64-apple-ios` slices, and the full suite reports `TEST SUCCEEDED`. Pushing the fix confirms it on the runner: run 38209186646 is green.
2. **The search field was unreachable on the three searchable screens.** With an inline navigation title, the iOS 27 default presentation created no search field at all: the captured accessibility hierarchy of the course screen contained no `SearchField`, no `TextField`, and no search button, so neither a user nor VoiceOver could reach assignment search. `ios/App/Theme.swift` now exposes `alwaysVisibleSearch(text:prompt:)`, which pins `.navigationBarDrawer(displayMode: .always)` on iOS and falls back to the default modifier elsewhere (the placement is unavailable on macOS, and the repository compiles every app source for macOS and Mac Catalyst). `CourseView`, `DocumentsView`, and `MailView` use it, and the UI cases now assert the returned search field on all three screens.

3. **The planner case drove a control in a way that only held on iOS 27.** Three problems sat in one case, and only the runner exposed them. Reading the inclusion switch's value immediately after tapping it failed with `Failed to get matching snapshot: No matches found for Descendants matching type Switch`. The hierarchy captured straight after the tap then showed the app sitting on the **Account tab** rather than a crashed planner: on the 402×874 runner display the math row was realized only at the very bottom edge, so the trailing-edge tap landed on the tab bar. The case now scrolls each target fully between the navigation and tab bars before touching it, asserts the exact demo estimates instead of re-reading the mutated switch, and asserts the Planner tab is still selected after the toggle. It passes locally on iOS 27 and on the runner.

The period/search case now submits the query to dismiss the keyboard and scrolls to the filtered row, because a lazy `List` does not realize rows that are off screen.

4. **The native client rejected the production session-cookie name, so a live sign-in could never load a grade.** `APIClient.sessionCookie(in:)` required the cookie to be named exactly `grademaxxing_session`, and `perform` sent that same hardcoded name back on every authenticated request. The deployed backend names its cookie `__Host-grademaxxing_session` whenever it is not running in development mode. A sign-in the backend had already accepted was therefore discarded as `APIError.invalidResponse`, which is the message "The school data could not be read. Try refreshing again.", and every later authenticated read would have sent a cookie name the server does not recognize. `SavedSession` now records the name the cookie was issued under, the client accepts either name, echoes back the name it received, and keeps it across rotation; a session saved before this field existed falls back to the unprefixed name. Only the authorized live run found this, because every synthetic fixture used the development name. The synthetic suite now covers the production name, the second `Set-Cookie` field the backend sends beside it, and rotation under that name.

   A related trap was checked and ruled out: `URLSession` joins the backend's repeated `Set-Cookie` fields into one comma-separated header, and Foundation does parse both cookies out of it — including the `__Host-` names — so the name check was the whole defect.

5. **The client refused the bare district host the service itself issues, so “Reconnect” could never succeed.** The portal service answers `POST /api/session` for a bare host (`ca-pleas-psv.edupoint.com`) and reports exactly that value back in its session payload; the native client stored it verbatim. `APIClient.login` then required `portal.scheme == "https"`, and `AppModel.reconnect` signs in again with that stored `account.domain`, so a reconnect always failed locally with “Enter a valid HTTPS district portal address, username, and password.” — even with the correct password, and without a request ever leaving the device. Live evidence: a read-only `POST /api/session` with the same account and the bare host answered `HTTP/2 200` in 1.6 s, while the app showed that message and no shell; the app's own sign-in screen reported the bare value as its field content. `APIClient.portalURL(from:)` now completes a scheme-less host as `https` and keeps every other guarantee: only an https URL with a host and without embedded credentials is accepted, `http://`, `ftp://`, embedded credentials, empty fields, and over-long domains still fail closed before any request. Live proof after the fix: the same bare host now reaches the signed-in shell. New synthetic check `bare portal host signs in, unsafe domains still refused` covers both halves.
