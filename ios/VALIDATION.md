# Native implementation validation

Evidence collected October 11, 2026. This is a first implementation. Full Xcode 27.0 (build 27A266a) with the iOS 27.0 simulator runtime is now installed in this environment, so the native sources have been **built and executed on iPhone simulators**: the shared `Grademaxxing` scheme builds and all seven synthetic UI cases pass on a small and a large iPhone. The `Native iOS checks` workflow is also green on the project's own runner (run 38209186646 at commit `3a86152`): 73 core checks, the project/formatting check, and all seven UI cases pass there under Xcode 16.4 with the iOS 18.5 runtime. Those runs found and fixed the defects described below. Native sources also pass `xcrun swift-format lint --strict --recursive App Sources Tests UITests Package.swift`.

This standalone repository contains an exported copy of the native sources. The web test/build results below were collected in the parent Grademaxxing checkout, not a web application in this repository. The GitHub Actions workflow builds and tests the same synthetic iPhone demo on an Xcode runner, and it passes. The two environments are not equivalent: the runner uses Xcode 16.4 with the iOS 18.5 runtime and picked an iPhone 16 Pro, while local validation used Xcode 27.0 with iOS 27.0, so neither substitutes for the other.

## Defects found and fixed by this run

1. **The app target built for a simulator slice that the local Swift package could not provide.** The generated project set no `ONLY_ACTIVE_ARCH`, so Debug builds compiled the app for both `arm64` and `x86_64` while the `GrademaxxingCore` package product was built for `arm64` only. The `x86_64` compile failed with `module file … is incompatible with this Swift compiler: built for incompatible target` and `Unable to resolve module dependency: 'GrademaxxingCore'`, failing both GitHub Actions runs (`Native iOS checks`, runs 38192021305 and 38192401393) as well as a local reproduction of the same command. `ios/scripts/generate-project.py` now sets `ONLY_ACTIVE_ARCH = YES` for Debug and `NO` for Release, matching Xcode's template default. Verified: before the change the app compiled `arm64` + `x86_64` and failed; after it the app compiles `arm64` only, with no `x86_64-apple-ios` slices, and the full suite reports `TEST SUCCEEDED`. Pushing the fix confirms it on the runner: run 38209186646 is green.
2. **The search field was unreachable on the three searchable screens.** With an inline navigation title, the iOS 27 default presentation created no search field at all: the captured accessibility hierarchy of the course screen contained no `SearchField`, no `TextField`, and no search button, so neither a user nor VoiceOver could reach assignment search. `ios/App/Theme.swift` now exposes `alwaysVisibleSearch(text:prompt:)`, which pins `.navigationBarDrawer(displayMode: .always)` on iOS and falls back to the default modifier elsewhere (the placement is unavailable on macOS, and the repository compiles every app source for macOS and Mac Catalyst). `CourseView`, `DocumentsView`, and `MailView` use it, and the UI cases now assert the returned search field on all three screens.

3. **The planner case drove a control in a way that only held on iOS 27.** Three problems sat in one case, and only the runner exposed them. Reading the inclusion switch's value immediately after tapping it failed with `Failed to get matching snapshot: No matches found for Descendants matching type Switch`. The hierarchy captured straight after the tap then showed the app sitting on the **Account tab** rather than a crashed planner: on the 402×874 runner display the math row was realized only at the very bottom edge, so the trailing-edge tap landed on the tab bar. The case now scrolls each target fully between the navigation and tab bars before touching it, asserts the exact demo estimates instead of re-reading the mutated switch, and asserts the Planner tab is still selected after the toggle. It passes locally on iOS 27 and on the runner.

The period/search case now submits the query to dismiss the keyboard and scrolls to the filtered row, because a lazy `List` does not realize rows that are off screen.

## What remains unverified

- **Native visual QA:** No screen was inspected by eye. Dark/light appearance, Dynamic Type sizes, layout on each device class, keyboard dismissal behaviour, and VoiceOver output remain unverified; the simulator runs assert state and identifiers, not appearance.
- **Background and lifecycle:** Background/resume, timeout, offline mode, app-switcher privacy shielding, and account switching have not been exercised.
- **Keychain and file protection:** The automated session tests use an in-memory vault and synthetic transport. On-simulator Keychain storage, device-only protection, and Quick Look preview rendering under file protection remain unverified.
- **Live school integration:** No designated account was provided or authorized. No live sign-in, portal read, student record capture, or real credential operation was performed.
- **Runner device coverage:** The workflow takes the first available iPhone simulator, so each run exercises one device class. Wider device coverage still rests on the local runs recorded above. Two local test runs also hit a transient XCTest runner bootstrap failure (`Early unexpected exit … handleStalledWait`) that cleared after shutting the simulators down; it did not reproduce in the runs recorded above.
- **Distribution:** Signing team, final icon, full privacy disclosures, feature parity, and TestFlight/App Store review remain on the roadmap. The privacy manifest is a scaffold and must be reconciled before distribution.
- **Physical device:** Nothing in this document is physical-device evidence. A passing simulator run does not establish on-device behaviour, signing, or performance.

The first failure of `swift test` established that Command Line Tools lacks Apple's Testing module. The check suite uses `swift run GrademaxxingChecks` and has no dependency on XCTest, Swift Testing, or external packages.
